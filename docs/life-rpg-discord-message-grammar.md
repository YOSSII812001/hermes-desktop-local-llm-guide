# Life RPG Discord Message Grammar

このドキュメントは、Hermes Desktop 上で動く Life RPG System が Discord へ配信するメッセージを、
どのような文法・設計原則で組み立てているかを一般化して説明する。個人の運用データ（ステータス値、
具体的なログ本文、家族・住所などの生情報）は一切含めない。パスは環境変数ベースの汎用表記
（`%LOCALAPPDATA%\hermes\rpg_system` など）で統一する。

## 背景: なぜ文法を統一するのか

Life RPG System は「ダン・コー式の人生ゲーム化」フレーム（Anti-Vision / Vision / 1年ミッション /
1か月ボス / 日次クエスト / 制約 / 日中割り込み / 夜の統合）を Discord 通知として実装したものである。
このフレームの核心は、**日々の小さな行動（daily levers）が、1か月単位の大きな目標（monthly boss）
にどうつながっているかが常に見える**ことにある。

通知が増えるほど、この接続は薄れがちになる。「今、何が起きたか」だけを伝える通知、演出だけで
行動につながらない通知が混ざると、ユーザーは何に反応すればいいか分からなくなる。これを防ぐため、
すべての配信メッセージに単一の文法を強制する。

## 統一文法: STATE → MEANING → ACTION

配信するメッセージは、必ず次の3要素をこの順序で含む。

1. **STATE（何が起きたか）**
   今この時刻に観測できる事実。敵、クエスト、ログ、カウンタの現在値など、解釈を挟まない生の状態。
2. **MEANING（旅にとっての意味）**
   その事実が上位フレームのどこに効くかを1行で示す。「これは月次ボス『◯◯』を前進させる」
   「この敵に負け続けた先が望まない未来」など、STATE を Vision/Anti-Vision/月次ボスに接続する。
3. **ACTION（次の1手と報告方法）**
   今すぐ、または今夜に取るべき一手と、その報告手段。「一文で返信＋『保存してください』」
   「追加の行動は不要、夜の精算で確定」など、必ずユーザーが次に何をすればいいかで終わる。

この3要素のいずれかが欠けている通知（特に MEANING や ACTION を欠いた「演出のみ」通知）は、
設計上の欠陥として扱い、文言修正の対象にする。

### 補足: 文言のワンパターン化を防ぐ（決定論的バリアント選択）

STATE/MEANING/ACTION という**構造**は固定でも、各要素の**具体的な言い回し**を単一の固定文字列に
してしまうと、同じ時刻・同じ分岐の通知が毎回同じ文言になり、ユーザーが慣れて読み飛ばすようになる。
これを避けるため、文言は複数バリアント（配列）として持たせ、`random` モジュールではなく日付等を
シードにした決定論的ハッシュ（敵選択 `select_enemy` と同じ SHA256 ベースの方式）で1件を選ぶ。
同じ日付なら常に同じ文言になる（再現可能・テスト可能）が、日をまたぐと表現が変わる。選択肢の
ラベルやカテゴリ区分（例: A/B/C/D の意味）自体は変えず、フレーズ部分だけがバリアント化の対象。

## 各時刻メッセージとレンダラーの対応表

Life RPG System は Windows のスケジュールタスクから Python のレンダー関数を呼び、Markdown を
生成して Discord へディスパッチする。時刻・レンダラー・役割の対応は次の通り。

| 時刻 | 役割 | 担当レンダラー（例） | STATE | MEANING | ACTION |
| --- | --- | --- | --- | --- | --- |
| 朝（例: 08:00） | 朝のクエストボード | `render_board` 相当 | 今日の敵、月次ボスカウンタ、今日のメインクエスト＋サブクエスト | メインクエストは「月次ボスカウンタの残りギャップが最大の項目」を決定論的に選ぶ。各クエストに「→ 月次ボス『◯◯』が前進」を付ける | 「やった行動を一文でこのチャンネルに返信＋『保存してください』」の固定フッター |
| 朝（例: 08:05） | 朝のナラティブ（章タイトル演出） | `render_morning_autonomy` 相当 | 章タイトル、敵の一言 | 「この敵に負け続けた先が望まない未来」という賭け金の提示 | 「詳細は直前のクエストボードを見る」という導線のみ（重複掲載はしない） |
| 日中（例: 16:00） | エンカウンター（分岐通知） | `render_encounter_autonomy` 相当 | 当日の保存状況に応じた分岐（未保存の督促／日中に既に保存済みの内容の引用／回復不足の兆候／報酬箱の予告） | 分岐ごとに、月次ボスカウンタや回復クエストへの意味付けを明示する | 分岐ごとに固有のACTION。保存済みの分岐では「追加の行動は不要、夜の精算で確定」で締め、督促系の分岐では選択式の一手を促す |
| 夜（例: 22:00） | 夜の精算（結果の物語化） | `render_settlement` 相当 | 敵との決着（撃破／取り逃がした）、クエストの達成/未達、獲得したポイント | 月次ボスカウンタの前日比（進捗の可視化） | 保存済みの「明日の一手」を引用。何も保存されていない日は、一文＋保存の呼びかけに切り替える |
| 夜（例: 22:10） | 報酬発表（新規分のみ） | `render_reward_autonomy` 相当 | 新規に解禁されたアイテム／称号／継続日数などの新規分のみ | 22:00の精算で確定済みの結果であることの明示（二重の演出にしない） | 新規なしの日は「新しい戦利品はなし、ポイントは夜の精算で確定済み」の短い1メッセージで終える |

実際の関数名・引数・データ構造はリポジトリ側の実装に依存するため、ここでは役割の対応関係のみを
示す。導入先のリポジトリで実装が変わった場合は、この表の「担当レンダラー」列だけを更新すればよい。

## 変更手順（この文法を保ったまま通知文言を直すとき）

1. 対象のレンダラー関数を特定する（上の対応表を参照）。
2. 変更後の文面が STATE / MEANING / ACTION の3要素をすべて含むかを確認する。
3. XP・ポイント・進捗などのゲーム内数値ロジックには触れない。文言・表示順序・見出しだけを直す
   （数値ロジックの変更は別のレビュー・別のテスト対象として扱う）。
4. 「演出のみ・行動につながらない」通知が新たに生まれていないかを確認する。ACTION 行が空、
   または「特にありません」で終わる分岐がある場合は MEANING か ACTION を補う。
5. dry-run 実行で実際の出力を目視確認してから配信する。

## 設計原則: ローカルLLMには構造生成をさせない

Hermes Desktop の Discord 連携はローカルLLM（例: Gemma 系モデル）を Gateway 経由で利用する構成を
想定できる。この構成には次のリスクがある。

- ローカルLLMに Markdown 構造・数値・進捗カウンタをその場で生成させると、ハルシネーションが混入し、
  ユーザーがゲーム内数値を実際より良く（あるいは悪く）誤認するおそれがある。
- 構造化出力の一貫性（見出しの順序、STATE/MEANING/ACTIONの区切り）をLLMの生成品質に依存させると、
  文言のわずかな揺らぎがユーザー体験の毀損に直結する。

そのため、次の役割分担を設計原則とする。

- **通知本文（テンプレート生成側）**: すべて決定論的なコード（Python のレンダー関数）が、保存済みの
  ログやカウンタといった正本データから Markdown を生成する。LLMはここに関与しない。
- **対話（会話側）**: ユーザーが Discord で返信し、それに対して応答するときだけローカルLLMが動く。
  この場合もLLMは「ツール呼び出しの結果」に基づいて話すことを徹底し、ツールを呼ばずに数値やステータスを
  語ることを禁止する。ツール結果に無い数値は絶対に言わない。
- 言い換えると、**「今何が起きているか」を伝える通知はテンプレート生成、「それについてどう話すか」は
  対話、という分離**を保つ。これにより、通知の正確性はコードの決定論性で担保し、対話の柔軟性は
  ローカルLLMに任せる、という両立ができる。

この原則は、Discord Bot に限らず、ローカルLLMを使う他の通知＋対話型エージェントにも一般化できる。
